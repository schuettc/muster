Optional

One bus across your machines.

By default muster keeps its state in a SQLite file that one daemon owns, so agents on your laptop and agents on your desktop are on two unrelated buses and cannot address each other. The hosted backend puts that state in your own AWS account instead. It is opt-in, it costs cents a month, and the local path is untouched if you never want it — the AWS SDK is not even compiled into the binary your devices run.

why

Nobody else's data passes through it.

This is not a service you sign up for. There is no account model, no user model, and no multi-tenancy — the deliverable is a CloudFormation template and a command that applies it. One DynamoDB table, one Lambda running the same daemon code your unix socket serves, and an HTTP API in front of it.

Your devices need no AWS anything No credentials, no profile, no region, no SDK. That is the entire reason a Lambda tier exists rather than devices talking to DynamoDB directly: DynamoDB authenticates with SigV4 and has no bearer-token equivalent, so a device talking to it would need real AWS credentials sitting on disk. A function can authenticate however it likes, and this one checks a shared bearer token over plain HTTPS.
The Lambda is muster Not a reimplementation of it. The same Dispatch that answers your unix socket runs in the function, over a DynamoDB implementation of the same store interface. Both implementations are held to one behavioural set by a shared conformance suite, so the two backends cannot quietly drift apart.
Your local daemon stays where it is It keeps the unix socket and it keeps tmux wake. In remote mode it forwards each request upstream instead of dispatching locally, and polls for messages written by your other machines. Every client above the daemon — the MCP server, the CLI, station — is unchanged.

deploy

One command, on one machine, once.

muster-deploy is a separate download from muster. It links the AWS SDK because talking to CloudFormation and S3 is its whole job, and bundling it into the device tarball would put AWS code in the archive every machine unpacks.

# install the deploy tool (not installed by default)
curl -fsSL https://muster.tools/install.sh | sh -s -- --with-deploy

# stand up the stack
muster-deploy --region us-east-1

It resolves your account from the ambient AWS credentials — AWS_PROFILE and AWS_REGION work as they do for any AWS command — creates an artifact bucket if you have none, downloads the Lambda zip matching its own version, applies the stack, waits, and prints the endpoint.

On a first deploy it generates your bearer token and writes it to ~/.local/share/muster/remote-token at mode 0600 — it does not print it. A printed secret ends up in scrollback, in tmux history, and plausibly in the context of a coding agent sharing your terminal. On an update it keeps the token already in the stack, so re-running it never rotates your fleet's credential by accident.

A name you own.

By default the endpoint is https://<api-id>.execute-api.<region>.amazonaws.com, where the api-id is generated when the API is created. That is fine until the day you delete and recreate the stack — you get a different URL and every device stops working at once. A custom domain is the only thing that makes the endpoint outlive the stack.

muster-deploy --region us-east-1 \
  --domain muster.example.com \
  --hosted-zone Z0123456789ABCDEFGHIJ

With a Route53 zone in the same account that one flag pair does everything: the certificate, its DNS validation, the API domain, the mapping, and the alias record — all owned by the same stack, so deleting it cleans up after itself. If your DNS lives elsewhere, validate an ACM certificate yourself in the stack's region and pass --cert instead. The "certificates must be in us-east-1" rule you may be remembering is a CloudFront rule and does not apply here.

Omitting --domain on a later deploy leaves an existing domain alone. Removing one is explicit, via --remove-domain — a routine redeploy to ship new function code must never tear down the hostname your devices resolve.

devices

Two exports and a token file.

On each machine that should join the bus:

muster device work-laptop
export MUSTER_BACKEND=remote
export MUSTER_REMOTE_URL=https://muster.example.com
# plus the token at ~/.local/share/muster/remote-token, mode 0600

Start the daemon from a shell that has those exports. One started without them comes up on the local SQLite bus and looks completely healthy — an empty roster on a device you believe joined is almost always this, and it is the single most time-wasting failure in the system.

To add a second machine, run muster-deploy -join on the one you deployed from. It prints the exports, the token, and a fingerprint for checking the copy arrived intact — with the token held separately from the paste-able block, so it never enters the new machine's shell history.

The token moves by hand, and that is not a gap It cannot be fetched from AWS: it is a NoEcho stack parameter, and more fundamentally the premise here is that a device needs no AWS credentials — a device with no credentials cannot fetch its own credential. Any channel you trust works: a password manager, AirDrop, scp, or typing 44 characters. Then compare fingerprints rather than the secret, with tr -d '\n' < ~/.local/share/muster/remote-token | shasum -a 256 | cut -c1-16.

naming

Say which machine you mean.

Name each machine before it registers anything. It is not retroactive, and it does two separate jobs.

It makes the roster legible Every agent registered from that machine carries the name, so you can ask an agent to "message the ci-cd session on my work laptop" and have it resolve — it matches the roster's device field, then sends to that row's alias. There is no device:alias syntax to learn; the model does the matching and muster supplies legible data. Unset, a machine falls back to its hostname reduced to lowercase and dashes, which is matchable but rarely what anyone says out loud.
It stops two machines claiming one alias An alias you do not choose comes from the tmux session name or the working directory — both identical on two machines with the same repos checked out. Registering is an upsert and the roster row is the identity, so without a device name the second machine to register takes the first one's alias, inbox and read-state. Session hooks re-register on every start, so the two would trade it back and forth with mail following whoever went last. With a name set, that machine's derived aliases become work-laptop-<name> and cannot collide. Aliases you type explicitly are never rewritten.
It is a file, not an export The name lives in <MUSTER_HOME>/device-name, so it survives reboots with no shell configuration and every process agrees on it however it was launched. $MUSTER_DEVICE_NAME overrides it for one shell. Naming a machine that has already registered is safe but does not rewrite existing rows — a seeded alias is a different alias, so use muster become <new-alias> to carry the identity and its mail across.

Addressing itself never gains a device dimension. An alias means the same agent from every machine on the bus, and aliases are unique bus-wide. Device is location; the alias is identity.

security

Read this before you deploy.

The API's default route carries no authorizer. AWS does not authenticate callers at its edge, so the endpoint is reachable by anyone who knows the hostname, and the bearer token checked inside the function is the only thing between a stranger and your whole bus — every message anyone has sent, and the ability to post as any agent on it.

Token entropy is what defends you The handler has no lockout and no per-caller memory. What bounds an online brute force is the API's route throttling, 20 requests per second by default — that turns guessing into a rate-limited attack rather than an unbounded one, but 20 guesses a second still adds up over months. muster-deploy generates 32 bytes from a CSPRNG; if you set one by hand, use openssl rand -base64 32 and never a passphrase.
A leaked token grants everything until you rotate One token is shared by every device, so there is no per-device attribution and no way to revoke a single machine without rotating all of them. The function accepts two tokens at once so a rotation can roll across your devices without downtime — a rotation procedure that breaks every machine simultaneously is one nobody ever runs.
This is a first step, not the destination Per-device hashed tokens, giving single-device revocation, are the intended next step; OIDC with short-lived tokens is where it is headed. The API is an HTTP API rather than a Lambda Function URL precisely because it can take a JWT authorizer as configuration when that time comes, and a Function URL cannot take one at any price.

cost

About forty cents a month.

Modelled on two devices, a ten-second poll, daemons up twelve hours a day, and a few hundred real operations a day — roughly 275,000 requests a month. Rates are AWS list prices for us-east-1; re-check before relying on them.

Lambda requests & durationInside the always-free tiers at this scale, which do not expire after twelve months. $0.
API Gateway$1.00 per million requests, and the only line with no free tier — about $0.28. This is what you pay for not needing AWS credentials on your devices.
DynamoDBOn-demand reads and writes, about $0.13. Storage is megabytes, inside the 25GB free tier.
TotalRoughly $0.41/month. Poll cadence is the lever that matters: polling every two seconds around the clock is about 2.6M requests and lands near $2.90, since every poll is a billable request whether or not it finds mail.

Set an AWS Budgets alert anyway. The stack's reserved concurrency bounds what a runaway poller or a stranger who finds your URL can spend, but a budget alert is what tells you it happened.

The full operator guide — the security model in detail, token rotation, upgrading the function, the known limitations, and troubleshooting — lives in docs/hosted-backend.md. Deleting the stack deletes the table and every message on the bus, with no backup and no export path.
